02 · Concepts

Think first, then build fast

Each lens is taught in about two minutes and then used straight away on the Thinking Canvas. The chain is: system → user → hypothesis → slice → prompt → test → reflect. Each visual plays as you scroll to it; press Replay to watch it again.

The map

Double Diamond

Day 1 and this morning covered the problem space. This session is Develop: explore solutions by prototyping, then converge on one MVP. If the peer test shows the wrong problem was defined, groups go back to the first diamond. That is normal, not failure.

Design Council (UK), 2004 · Framework for Innovation

What “viable” means

A thin slice, not a wide base

A prototype asks whether people understand it; an MVP asks whether they will use or pay for it; a product asks whether it scales. The MVP is one core job that works, does not break in the demo, needs no help, beats the old way, feels good and matters. That is why the canvas allows only three features.

After S. P. Anderson’s UX hierarchy of needs (2011), building on A. Walter (2011); MVP-slice view as drawn by B. Waldock, beingagile.co.uk

How an MVP is born

Design thinking + Lean UX + Agile

Design thinking climbs from needs to a concept. Lean UX turns the concept into a hypothesis and the smallest thing that tests it. Agile takes over with short build–measure–learn loops: Sprint 1, the peer test and Sprint 2. AI shrinks each Build step to minutes.

Build–Measure–Learn: E. Ries, The Lean Startup (2011)

Lens 1 · Canvas box 1

Systems thinking

Ask why the problem keeps happening and who else is part of it. An app that only reacts to events is weak; one that changes a structure (a shared live schedule) is strong. The people in the system, such as lab staff, the faculty office and other groups, decide whether the MVP can work.

Lens 2 · Canvas box 2

Design thinking

Start from a person and an insight, not a feature list. The point-of-view sentence forces three things: a specific user, a real need (a verb, not a feature) and an insight into why it is hard today. The “How might we…?” question turns it into an open design challenge the AI build answers.

Empathise · Define · Ideate · Prototype · Test, after the Stanford d.school

Box 2 → ROLE & GOAL in the prompt

Lens 3 · Canvas box 4

Computational thinking

Think like a computer before you prompt one. Decompose the core job into steps, spot a familiar pattern, abstract away everything that does not test the hypothesis, and write the rule precisely. Each habit fills one part of the build prompt.

J. M. Wing (2006), Communications of the ACM 49(3)

Box 4 → CORE FLOW + FEATURES

Lens 4 · Canvas box 3

Lean UX hypothesis

Every idea hides one assumption that can kill it. Write it as a hypothesis a test can prove wrong: who, what they will do, why, and the signal you will see. The signal must be visible in today’s two-minute peer test.

Format adapted from J. Gothelf & J. Seiden, Lean UX (2013)

03 · Generation-time playbook

Nobody watches the progress bar

A first build takes 2–5 minutes and each tweak 1–3 minutes. Run a simulated build to see what every role does while the AI works, then check the fixes for builds that misbehave.

0:00 / 3:00 (sped up)

Builder

while it generates

Writes the next prompt: one change only.

User

while it generates

Writes 2–3 test steps for this build.

Scribe

while it generates

Drafts the 20-second demo script; logs prompts.

Researcher

while it generates

Prepares sample data and app wording (RM, kolej, BM/EN).

Still generating after 5 minutes

Wait one more minute, then refresh and resubmit a shorter prompt.

First build fails twice

Paste the same prompt into a backup tool: Lovable or Bolt.new.

Same error after two loops

Undo to the last working version and split the change into smaller prompts.

Out of free credits

The next member signs in with their own account and continues from the saved prompts.

A WOW feature breaks the app after 12.06

Undo it and demo the working version. A working simple app beats a broken clever one.
